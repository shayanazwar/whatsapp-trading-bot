# Render deployment

1. Create a **new private GitHub repository** named `kronos-mexc-intelligence` and push this project. This package does not create cloud resources or access your Render account.
2. In Render, create a Blueprint from the repository and review `render.yaml` before applying it.
3. Set `APP_SECRET_KEY` to a random value at least 32 characters long, `ADMIN_USERNAME`, and `ADMIN_PASSWORD` (14+ characters). Set the database connection reference created by the Blueprint.
4. Confirm the web, market, inference and backtest services use the same PostgreSQL database and commit.
5. All four containers run `python -m app.migration_lock` at startup. PostgreSQL advisory locking serializes concurrent Alembic upgrades if Render starts services together. The market, inference and compute workers are mandatory: the web service accepts and persists jobs but does not consume them. Confirm each Render worker is `Live`, has the same `DATABASE_URL` as web, and logs `[WORKER_STARTED]` plus fresh heartbeats before submitting jobs. Verify `/healthz`, `/readyz`, then run WhatsApp `WORKERS`, `QUEUE`, `HEALTH`, `ANALYZE BTCUSDT`, and `STATUS <job-id>`.
6. The inference and backtest workers are CPU-first (the Blueprint currently requests 2 CPU / 4 GB RAM each); the web and market services use 0.5 CPU / 512 MB RAM, and PostgreSQL uses 0.5 CPU / 1 GB RAM. These are requested Render plan IDs and availability must be checked in the account. Both model-enabled workers clone the pinned Kronos source during image build; Hugging Face weights download on first inference to each worker's own persistent disk. Benchmark real inference time and memory with 1,000 paths before increasing throughput or lowering either plan.

Render services are independent processes. A disk attached to one service is not a shared disk for other services. The inference worker writes durable forecast artifacts through PostgreSQL; its model cache is local to its own disk. Do not use a local container path for cross-service forecasts; PostgreSQL is the only implemented artifact backend in this release. Render does not publish a dedicated GPU service plan in its standard service plan list, so high-throughput inference may need an external GPU inference provider behind a private authenticated URL. Keep the web service lightweight.

The provided Blueprint is a deployable starting configuration but it cannot prove that the user's account, region, plan availability, billing or resource limits permit deployment. Validate it in Render before applying. WhatsApp command/status messaging is supported only when valid Meta credentials, webhook signature verification, and the sender allowlist are configured. Direct trade-signal delivery remains intentionally blocked; detailed research outputs are available in the authenticated dashboard. Use `META_ACCESS_TOKEN`, `META_PHONE_NUMBER_ID`, `META_VERIFY_TOKEN`, and `META_APP_SECRET` as the canonical environment variable names. The older `WHATSAPP_*` credential names are accepted only as fallbacks; `META_*` takes precedence when both are present.
